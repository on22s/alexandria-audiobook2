# 批量生成

[中文主页](Home-CN.md) · [English](Batch-Generation.md)

应用如何一次渲染许多行，以及如何调优。

## 你的渲染走哪条路径

| TTS 模式（Setup） | **Render Pending** / **Regenerate All** 做什么 |
|---|---|
| `local`（内置引擎） | **批量**渲染：每次调用 Qwen3-TTS 处理多行，按声音类型分组 |
| `external`（Gradio 服务器或服务器池） | 每行一次调用，并行发送 |

批量渲染是快路径：在中端显卡上约为实时的 3–6 倍。它每次原生模型调用使用一个 seed。**Batch Seed** 留空或为 `-1` 时，每次调用都遵循实际生效的、保存/版本选中的声音 seed；声音 seed 为负则该次调用不设 seed。非负的 **Batch Seed** 会覆盖所有已保存的声音 seed，并像以前一样为每个已有子批次重新设 seed。逐行路径同样使用已保存的声音 seed，适用于所有声音类型，但更慢。

原生 custom/clone/LoRA 调用无法为每一行单独设置 seed。按长度排序并应用条目/内存上限之后，只要实际生效的 seed 发生变化，批次就会进一步拆分。seed 相同则保持原生批量；不同 seed 交错时可能退化为逐行一次调用，从而降低吞吐。这是有意为之，而不是静默忽略已保存的 seed。共享的非负批次覆盖会保留原有的批次划分，但改变使用哪个 seed。给多行调用设 seed 并不保证得到与逐行分别渲染相同的波形，也不保证整本书听感上的声音身份一致。

## 声音类型的渲染顺序

1. **Custom 声音**——原生批量（最快）。
2. **Clone 声音**——按说话人批量。
3. **LoRA 声音**——按适配器批量。
4. **Voice Design**——逐行处理，因为每行的描述可能不同。

行数最多的类型通常先处理，所以全书大部分内容很早就完成。

## 每种类型如何批量

- **Custom**——收集所有 Custom 行，按说话人分组，按长度排序，再拆成子批次。每个子批次是一次携带文本列表的调用。
- **Clone**——按**说话人**分组，因为每个说话人有自己的参考音频。声音提示词对每个说话人只构建一次并缓存。
- **LoRA**——按**适配器**分组，因为每个适配器有自己的权重。每行的 instruction 和角色风格随行一起传递。
- **Voice Design**——在所有批量类型完成后逐个渲染。

## 子批次

语音模型会一直生成到批次中最长的文本结束，所以同一批次里较短的文本会在填充上浪费 GPU 时间。子批次把长度相近的文本分到一起，以减少这种浪费。

工作方式：

1. 按文本长度排序，最短的在前。
2. 依次遍历，收集一组。
3. 当最长文本超过最短文本的 *ratio* 倍，**并且**该组已有至少 *min size* 行时，开始新的一组。
4. 在实际生效的 seed 变化处进一步细分每组；由此得到的每组各自成为一次调用。关闭长度比例拆分仍然遵守内存/手动条目上限和 seed 边界。

| 设置（Setup） | 默认值 | 含义 |
|---|---|---|
| Sub-batching | 开 | 按长度拆分批次 |
| Min Sub-batch Size | 4 | 长度比例拆分前的最小值；上限和 seed 可以把组拆得更小 |
| Length Ratio | 5 | 允许的最长与最短之比上限 |

**示例：** ratio 为 5 时，10、15、20、50、55 和 200 字符的文本会拆成 [10, 15, 20]、[50, 55] 和 [200]，因为 200 大于 5 × 10。

## 调优

**先点 Auto-Configure。** 它读取你的显卡显存，并根据在 RX 9070 XT 上的测量设置批处理参数（模型本身约占 4.2 GB；4、8、16 行的批次峰值约为 7.3、9.6、11.8 GB）。

| 设置 | 作用 |
|---|---|
| TTS Mode | 批量渲染需要 `local` |
| Parallel Workers | 本地渲染的批大小；Auto-Configure 会按显存设成 1–4。装得下时越多越快：在 RX 9070 XT 上，1 / 4 / 16 个 worker 的渲染速度是实时的 1.2 / 2.2 / 3.9 倍（2026-09-28） |
| Max Items/Batch | 每批行数的上限 |
| Compile Codec | 一次性 30–60 秒预热后，解码快 3–4 倍 |
| Sub-batching | 开——减少填充浪费 |

上游 Alexandria 在 24 GB 的 RX 7900 XTX 上测过更大的 worker 数（20–60）。本分支没有重新测量这些数字；请从 Auto-Configure 开始，只在显存允许时提高数值。

### 上游基准（RX 7900 XTX，24 GB，ROCm 6.3）

| 配置 | 速度 |
|---|---|
| 逐行 | 约 1 倍实时 |
| 批量，不编译编解码器 | 约 2 倍实时 |
| 批量并编译编解码器 | **3–6 倍实时** |
| LoRA，逐行 | 约 0.5 倍实时 |
| LoRA，批量 | **约 5.5 倍实时** |

一本 273 行的有声书（约 54 分钟音频）在批量渲染并编译编解码器的情况下约 16 分钟完成。

## 显存

- 子批次之间，应用会运行 `gc.collect()` 和 `torch.cuda.empty_cache()`，防止内存碎片。
- 批次开始前，余量检查会拒绝装不下的批次。
- 各类声音分别渲染，所以峰值显存是最大一组的用量，而不是总和。
- 如果显存不足，调低 **Parallel Workers** 和 **Max Items/Batch**。
- 同一张卡上的语言模型会占用 TTS 的显存。如果你的 LLM 托管在别处，在 Setup 里打开 **Provider request options**，把 **Runs on this machine's GPU?** 设为 **No**。

## 编解码器编译

开启 **Compile Codec** 后，`torch.compile` 会在编解码器解码器首次使用时进行优化。这会一次性多花 30–60 秒，之后本次会话剩余时间的解码都快 3–4 倍。它不会为每个批次重新编译——只在应用重启后才会。

## AMD（ROCm）说明

应用会自动套用 ROCm 专用修复；你不需要配置任何东西：

- **MIOpen 快速查找模式**——防止工作区分配失败。
- **Triton AMD flash attention**——为 Whisper 编码器启用 flash attention。
- **一个 `triton_key` 兼容层**——修复 pytorch-triton-rocm 上的 `torch.compile`。
- **APU**（660M/680M/780M 这一类）以 fp32 运行 TTS，因为 bf16 在这些设备上有问题。
