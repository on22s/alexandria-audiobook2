# Thunder Compute をいつ使うか（そして何に使うか）

このプロジェクトのための判断ガイドです。**既定はローカル**で、Thunder は例外であり、基準ではありません。

あなたのハードウェア：**AMD Radeon RX 9070 XT**（16 GB、RDNA4/ROCm）で、`localhost:1234` の LM Studio を動かしています。アプリの既定は `llm_mode: local` で、Thunder のリモートプロファイルも設定できます。何も課金されていないと決めつける前に、必ず `tnr status` を確認してください。

---

## 1. 一行のルール

> ジョブが**ローカルではまったく動かない**とき、またはローカルだとあまりに長くかかって実時間の方が金額より重要になるときに Thunder を使います。それ以外はローカルのままにします。

**A6000 で 1 時間 $0.35**（価格は 2026-07-18 時点）なら、数時間の作業ではコストが決め手になることはまれです。決め手は **VRAM**、**CUDA**、**実時間**です。

---

## 2. Thunder を使う場合

| 理由 | ローカルで失敗する理由 | 推奨 GPU |
|---|---|---|
| **モデルに 16 GB 超の VRAM が必要** | 9070 XT は約 16 GB が上限。大きいモデルや長いコンテキストは読み込めない。 | A6000（48 GB）、$0.35/時 |
| **CUDA 専用のコード** | あなたのカードは ROCm。CUDA カーネルを前提とするもの（一部の `xformers`／`triton`／`sageattention`／`flash-attn` のビルド、上流の ML wheel の多く）は動かない。 | A6000 / L40 |
| **デスクトップを返してほしい** | ローカルの LLM 作業が GPU を占有し、グローバルの GPU ロックがアプリのほかのすべてのタスクを止める。 | A6000 |
| **測定済みの Gemma エンドポイントでのペルソナ生成** | A100 は本番の discovery/compile コホートを 2.27 倍速く完了した。 | A100 80 GB |
| **ローカルで実際に OOM したワークロード** | 測定した A100 は、LoRA 学習を含むすべての試験した TTS と Voice Lab の段階で遅かった。速度の想定ではなく容量が障害になっているときだけ使う。 | 観測した VRAM 需要に合わせて選ぶ |

## 3. Thunder を使わない場合

- **CPU だけの作業。** Audacity、M4B、Voice Lab の命名は両方のマシンで測定し、3 つともローカルが速かった。
- **短い、または対話的なジョブ。** セットアップの手間（作成 → SSH → モデル読み込み → ポート転送）が、数分の推論をはるかに上回る。
- **並列性を追いかけること。** §4 を参照。これが最大の落とし穴。
- **GPU 律速だと確認していないもの。** まず確認する。I/O や LLM の遅延の問題を直すために GPU を借りない。

---

## 4. Thunder が買うのは VRAM と CUDA — 速度は測定が必要

これは理論ではなく測定済みで、ここで最も直感に反することです。

> 生のレポートがバージョン管理されていない過去の Thunder **A6000** の実行では、`concurrency`／`parallel` を **1 より大きくすると遅く**なり、**4 でクラッシュ**しました。concurrency は **1** に保ってください。`parallel` を自動でスケールしないでください。

ローカルでは、`lmstudio_settings.IDEAL_SETTINGS` が VRAM の安全のために意図的に `parallel: 1` を固定しています。これは意図したトレードオフ（Rule 9）であり、GPU を借りて「直す」バグではありません。つまりリモートにしても同時リクエストが解禁されるわけではありません。並列性で 4 倍のスループットを期待して A6000 を借りると、4 倍払って 1 倍未満しか得られません。

Thunder は **VRAM の余裕と CUDA** のために借ります。正確なモデル／ランタイムを測定せずに、トークンあたりの速度やファンアウトが良くなると想定しないでください。

ボトルネックは GPU の仕様だけでなく、ソフトウェアの経路全体に依存します。A100 は計算が重いはずの LoRA 学習の較正で負けました。ベンチマークは原因をプロファイルしておらず、セットアップ、データ、小さいバッチ、カーネル、フレームワークのオーバーヘッドが寄与している可能性があります。本番に近い形の測定なしに、理論上の計算上の利点を配置のルールに格上げしないでください。

### このキャンペーンで知られている交絡

このキャンペーン自身のハーネスに、後から 4 つの抜けが見つかりました。どれも下の数値が捏造だという意味ではありませんが、どれも制御されていません。再実行で対応するまでは、この節の結論は暫定的なものとして扱ってください。台本生成と台本レビュー（両方のターゲット）はその後、修正されたハーネスで再実行済みです。最初の 2 つの箇条書きの下の検証メモを参照してください。残る 2 つ（使用率のサンプリング、規模を上げたときのスループット）は、この文書のすべての TTS/LoRA/VoiceLab の数値にまだ当てはまり、再実行はまだです。

- **Torch/CUDA ビルドの不一致。** ローカルは Torch 2.10.0+ROCm7.0、Thunder は古い Torch 2.7.0+CUDA12.6 でした。以下の TTS/LoRA/VoiceLab の比較はすべて、2 つの GPU ではなく 2 つの異なるソフトウェアスタックをまたいで測定されています。ベンチマークのハーネスは現在、両側の Torch バージョンを記録し、1 回のプリフライトで両方を集めたときに食い違えば `benchmark_environment.verify_comparable_environments` が大きく警告します。**2026-07-18 に検証済み：** Thunder の Torch を 2.10.0+CUDA12.6 にその場で更新し（ローカルのマイナーバージョンに一致。torchaudio/triton/CUDA の依存も一緒に更新し、transformers/peft/qwen_tts は触らず再 import も正常）、台本生成／レビューの再実行でプリフライトのチェックがきれいに通りました。TTS/LoRA/VoiceLab の段階は、そろえた Torch ではまだ再実行していません。
- **NVIDIA 向けの使用率の計測がなかった。** 下の CustomVoice の「A100 は使用率が約 15% だった」というメモは、その場限りの繰り返していない観測でした。`gpu_stats.py` には AMD 用の `rocm_smi_utilization` しかなかったためです。`tts_benchmark.py` は現在、生成呼び出しのたびに、新しい `gpu_stats.sample_gpu_utilization()`（NVIDIA か AMD の存在する方）で `mean_gpu_utilization_pct` をサンプリングするので、今後の実行では目分量の余談ではなく実際の指標として得られます。実際の TTS ハードウェアではまだ試しておらず、この検証の回では LLM ベースの段階だけを再実行しました。
- **LLM ベースのベンチマークが、デコードだけでなくネットワークの往復も計っていた。** 台本生成／レビュー、ペルソナ、ニックネーム検出は以前、ローカルのオーケストレーターから設定済みの LM Studio エンドポイントを直接呼んでいました。「thunder」ターゲットでは、SSH で転送した HTTPS トンネルを通るインターネットの往復が、1 回だけでなくすべてのフィクスチャ×繰り返しの呼び出しに織り込まれていました。最も分かりやすいのはニックネーム検出の 2 秒未満の合計で、RTT が 1 回あるだけで報告時間が 2 倍になりえます。最初の緩和（2026-07-18）：各 LLM 段階のランナーが、レポートごとに `network_rtt_seconds` のベースライン計測を 1 回記録します。台本生成／レビューではローカル 0.083 秒に対し Thunder 0.53〜0.54 秒（約 6.5 倍）で、交絡が実在することが確認されました。ただしこれは交絡を*測る*だけなので、実際の修正が続きました。`llm_benchmark_worker.py` はループ全体を SSH 経由で **Thunder ホスト上で**実行します（TTS/LoRA/VoiceLab のワーカーの形を踏襲し、ステージしてからリモートで実行し、公開転送 URL ではなくそこから `localhost` を叩きます）。これによりネットワークが問題になるのはバッチを開始する 1 回の SSH 往復だけで、LLM 呼び出しごとではありません。マニフェストの `settings.remote_root`／`remote_python` が設定されていれば、TTS 系の段階と同じく 4 つすべての LLM 段階で使えます。実際のハードウェアではまだ試しておらず（これが入った時点で稼働中の Thunder インスタンスがなかった）、SSH をモックした単体テストのみです。
- **TTS/LoRA/VoiceLab のベンチマークはすべて単一ストリームか小さいバッチ**（6 回の連続生成、下のバッチ上限は 16 以下）で、A100 が最も弱くコンシューマー GPU が最も強い形です。ここではデータセンター GPU が作られた規模でのスループットの領域を何も試していません。既存の `tts_vram_benchmark.py --sizes 32 64`（`--sizes` フラグはもともと任意の上限リストを受け取るのでコード変更は不要）は、その大きな上限で Thunder ではまだ実行していません。「TTS はローカルが勝つ」が 16 以下だけでなくすべてのバッチサイズで成り立つと結論する前に、次に行うべき実験です。

**アーカイブの慣例：** このキャンペーンの 13 段階のうち、今日また必要になったときに元の `reports/benchmarks/<preflight_id>.json` が残っていたのは 2 つだけでした。残り 11 は数値をこの文書に写した後に片付けられており、正確なフィクスチャを再構成するのに実際に手間がかかりました。今後は、一時コピーを消す前に段階のレポートを [`../benchmarks/raw/`](../benchmarks/raw/)（git で追跡、そこの `README.md` を参照）へアーカイブし、フィクスチャの選択を一からやり直さずに、どの段階の数値も再検証・再実行できるようにしてください。

### A100 の台本生成ベンチマーク — 2026-07-18

これは小規模な対照コホートであり、汎用的な GPU の順位ではありません。同じ Gemma 4 E4B Q8 モデル、過去の約 6,000 文字のチャンク 3 つ、それぞれ 3 回の繰り返し、`max_retries: 0` を両方のマシンで使いました。再試行ゼロは 1 回の試行での素の信頼性を測るもので、本番の完了率ではありません。

| 環境 | 成功 | 合計時間 | 成功した呼び出しの平均 | 集計の完了レート |
|---|---:|---:|---:|---:|
| RX 9070 XT、32,768 コンテキスト、parallel 2 | 9 回中 7 回 | 329.5 秒 | 43.9 秒 | 65.5 tok/s |
| A100 80 GB、98,304 コンテキスト、parallel 2 | 9 回中 7 回 | 679.4 秒 | 94.9 秒 | 32.9 tok/s |
| A100 80 GB、32,768 コンテキスト、parallel 2 | 9 回中 6 回 | 1,032.7 秒 | 105.3 秒 | 20.6 tok/s |

失敗は主に確率的な早期停止か構造的に不正な出力で、品質のゲートは不完全な台本を正しく拒否しました。Thunder のコンテキストを下げても単一ストリームの速度は**直らなかった**ので、98k の KV 割り当てが実証されたボトルネックではありませんでした。

32,768 コンテキストで本番に近い形の 3 回の試行による並列性のスイープでは、次の結果でした。

| LM Studio の parallel / 同時リクエスト | 集計の完了レートの中央値 |
|---|---:|
| 1 / 1 | 43.5 tok/s |
| 2 / 2 | 17.9 tok/s |

parallel 2 は 59% 遅かったため、安全ポリシーにより 4/8/16 の前で止めました。この正確な A100/Gemma/LM Studio の組み合わせでは、**parallel 1 が測定上の最適**です。実用的な推奨は、Gemma の台本生成をローカルの RX 9070 XT に置くことです。この A100 は VRAM/CUDA や別の測定済みワークロードが正当化するときだけ使います。このデコードの結果を TTS、学習、Voice Lab に外挿しないでください。それらの別々の測定結果は下に記録しています。

現在の保護された `REMOTE_IDEAL_SETTINGS` は依然として `parallel: 2` を設定し、リモートの自己修復がその値を戻すことがあります。parallel 1 という測定結果は、その安全に関わる本番設定を意図的に変更して検証するまでの助言であり、このガイドが黙って上書きするものではありません。

### A100 の台本レビューベンチマーク — 2026-07-18

本番の `review_batch` 経路を、Volumes 3、9、10 からの不変の 25 項目のバッチ 3 つで、3 回の繰り返しと再試行ゼロで測定しました。両方の環境で同じモデルと 32,768 コンテキストを使い、Thunder は測定済みの parallel 1 の最適値、ローカルは parallel 2 の構成のままでした。

| 環境 | 成功 | 合計時間 | バッチの平均 | 集計の完了レート | 単語比の平均 |
|---|---:|---:|---:|---:|---:|
| RX 9070 XT ローカル | 9/9 | 238.3 秒 | 26.5 秒 | 63.9 tok/s | 0.9993 |
| A100 80 GB Thunder | 9/9 | 474.3 秒 | 52.7 秒 | 32.0 tok/s | 0.9978 |

どちらも構造を保ち、本番の 95〜105% のテキスト損失ゲートの範囲内でした。このコホートでは Thunder に信頼性の利点はなく、ほぼちょうど 2 倍遅い結果でした。このモデル／ランタイムでは **Gemma の台本レビューはローカルに保ってください**。これは台本生成の結果を補強しますが、LoRA 学習の性能については何も述べていません。

### A100 の CustomVoice TTS ベンチマーク — 2026-07-18

本番の `TTSEngine.generate_custom_voice` 経路を、同じ短／中／長のナレーションのフィクスチャ 3 つ、固定した seed、生成トークン上限 1,024、フィクスチャごとに 2 回の繰り返しで測定しました。モデルの読み込みと生成は別々に計りました。両方の環境に `flash-attn` がなく、手動の PyTorch attention 経路を使っていました。ローカルは Torch 2.10.0+ROCm 7.0、Thunder は Torch 2.7.0+CUDA 12.6 でした。LM Studio は両方のマシンで常駐したままでした。

| 環境 | 成功 | キャッシュ済みモデルの読み込み | ウォーム時の音声スループット | クリップした出力 |
|---|---:|---:|---:|---:|
| RX 9070 XT ローカル | 6/6 | 6.2 秒 | 1.18 audio-sec/wall-sec | 0/6 |
| A100 80 GB Thunder | 6/6 | 21.8 秒 | 0.28 audio-sec/wall-sec | 0/6 |

固定した seed により、各マシン内では繰り返し間で同一のハッシュが出ました。バックエンドをまたぐとハッシュと長さが少し違いましたが、Torch/GPU カーネルが違えば当然です。WAV はすべて有効な 24 kHz モノラルの PCM で、無音でなく、クリップもしていませんでした。

この正確な直列の CustomVoice 経路では、ローカルの RX 9070 XT が実時間 1 秒あたり約 **4.2 倍多くの音声**を出し、すでに実時間より速かったです。A100 は観測中おおむね使用率 15% 程度で動いていました。つまり A100 の大きな VRAM 容量は、単一ストリームの速度には結び付きませんでした。このソフトウェアスタックでは、直列の CustomVoice 生成をローカルに保ってください。ネイティブのリストバッチは下で別に測定しました。LoRA 学習は別のコホートなので、その結果も下で別に測定しました。

#### CustomVoice ネイティブバッチの容量

本番の `_local_batch_custom` 経路を、各マシンで同じ 16 個の長さの混ざったソースチャンクでスイープしました。8 を超える上限は助けになりませんでした。16 では長さ比による分割が依然として 2 つのサブバッチを作り、自己回帰のパディングがスループットを下げました。最初の容量スイープでは次の結果でした。

| バッチ上限 | RX 9070 XT の実時間倍率 | A100 の実時間倍率 | A100 の失敗 |
|---:|---:|---:|---:|
| 2 | 1.71× | 0.47× | 0/16 |
| 4 | 3.12× | 0.86× | 0/16 |
| 8 | 4.93× | 1.32× | 0/16 |
| 16 | 4.03× | 0.89× | 0/16 |

このスイープで 2 つの測定の欠陥が分かりました。ツールが最後のサブバッチの VRAM ピークしか報告せず、TTS の seed も固定していませんでした。どちらも確認の実行の前に直しました。`batch_seed=42` と上限 8 で、ローカルは 16 個の入力を **87.3 秒**で完了し、ピークは 9.64 GB でした。A100 は **210.6 秒**で完了し、ピークは 10.12 GB でした。seed が同じでも ROCm/CUDA のカーネルで出力の長さは変わるため、同じ入力での実時間を主な比較にします。ローカルが **2.41 倍速い**です。測定上の最適は両方のマシンで上限 8 で、この長さの混ざったワークロードでは A100 の容量があってもそれを超える有効なスケーリングはできませんでした。

#### Base モデルの声のクローン

本番のクローン経路は、両方のマシンで同じハッシュ検証済みの Watson 参照音声と文字起こしを使いました。短／中／長の目標テキスト 3 つを、固定した seed と 1,024 トークンの上限で 2 回ずつ実行しました。モデルの読み込み、再利用可能なクローンプロンプトの構築、生成は別々に計りました。

| 環境 | 成功 | Base の読み込み | プロンプトの構築 | 6 回の生成 | 集計の音声スループット |
|---|---:|---:|---:|---:|---:|
| RX 9070 XT ローカル | 6/6 | 6.44 秒 | 0.99 秒 | 44.8 秒 | 実時間の 1.15 倍 |
| A100 80 GB Thunder | 6/6 | 30.14 秒 | 7.20 秒 | 228.3 秒 | 実時間の 0.25 倍 |

出力はすべて有効な 24 kHz モノラルの PCM で、バックエンド内では決定的で、無音でなく、クリップもしていませんでした。同じ目標入力では、ローカルの生成が **5.09 倍速い**です。これらの Torch/Qwen スタックでは、直列の Base モデルのクローンをローカルに保ってください。

続いて、ネイティブのクローンバッチの経路を、CustomVoice で使ったのと同じ 16 個の決定的で長さの混ざった入力でスイープしました。

| バッチ上限 | RX 9070 XT の時間 / 実時間倍率 / ピーク | A100 の時間 / 実時間倍率 / ピーク |
|---:|---:|---:|
| 2 | 80.5 秒 / 1.91× / 6.13 GB | 322.3 秒 / 0.47× / 5.72 GB |
| 4 | 45.5 秒 / 3.45× / 7.17 GB | 183.7 秒 / 0.84× / 7.21 GB |
| 8 | **37.3 秒 / 4.27× / 9.25 GB** | **107.8 秒 / 1.43× / 10.17 GB** |
| 16 | 40.1 秒 / 3.88× / 11.84 GB | 153.5 秒 / 1.02× / 13.87 GB |

両方のマシンと 4 つの上限にまたがる 128 個の出力はすべて正常に完了しました。上限 8 が両方の GPU で測定上の最適です。その共通の最適値で、同じ入力の実時間ではローカルが **2.89 倍速い**です。上限 16 は、最後の長い 3 つのチャンクがより遅い 2 つ目のサブバッチを作ったため悪化しました。A100 にはまだ約 67 GB の未使用があり、追加の容量が答えではありませんでした。

#### VoiceDesign のプレビュー

本番の `generate_voice_design` の呼び出しを、3 つの異なる声の説明と短／中／長の目標テキスト、それぞれ 2 回の固定 seed の繰り返し、1,024 トークンの上限で測定しました。ベンチマークには実際のプレビュー WAV の作成も含み、そのファイルをベンチマークの出力ディレクトリーへ移します。

| 環境 | 成功 | キャッシュ済みモデルの読み込み | 6 回の生成 | 集計の音声スループット |
|---|---:|---:|---:|---:|
| RX 9070 XT ローカル | 6/6 | 6.07 秒 | 40.7 秒 | 実時間の 1.15 倍 |
| A100 80 GB Thunder | 6/6 | 24.21 秒 | 173.9 秒 | 実時間の 0.27 倍 |

同じ入力の実時間では、ローカルの VoiceDesign 生成が **4.27 倍速い**です。出力はすべて有効で、無音でなく、クリップもしていませんでした。ローカルの繰り返しはビット単位で同一でした。A100 では中くらいの長さの繰り返し 1 つが、固定 seed にもかかわらずサンプル単位でわずかに異なりましたが、長さと健全性の指標は実質的に同一でした。CUDA の VoiceDesign の出力をビット単位で決定的だと保証されたものとして扱わないでください。これらのソフトウェアスタックでは、VoiceDesign のプレビューと設計した声のチャンク生成をローカルに保ってください。

#### LoRA TTS の推論

本番の LoRA 経路は、両方のマシンで同じハッシュ検証済みの Watson アダプター、seed、プロンプトを使いました。モデル／アダプターの読み込み、再利用可能なプロンプトの構築、ウォーム時の生成を別々に計りました。

| 段階 | RX 9070 XT | A100 Thunder |
|---|---:|---:|
| モデル＋アダプターの読み込み | 4.54 秒 | 23.43 秒 |
| プロンプトの構築 | 0.86 秒 | 7.02 秒 |
| ウォーム時の生成 | 5.48 秒 | 32.05 秒 |

ローカルのウォーム時の生成が **5.85 倍速い**です。両方の環境で、繰り返しをまたいで健全で決定的な出力が出ました。このアダプター／モデルのスタックでは LoRA の推論をローカルに保ってください。

### ペルソナとニックネームの LLM ユーティリティ

高度なペルソナのベンチマークは、TTS を再度生成するのではなく、意図的にプレビューの境界を捉えました。各ターゲットが、同じ 2 話者のフィクスチャに対して discovery の呼び出し 1 回と compile の呼び出し 2 回を行いました。Thunder は 17.557 秒で完了し、ローカルは 39.885 秒でした。**Thunder が 2.27 倍速く**、どちらも話者と証拠の網羅率が 100% でした。これは A100 が実時間で勝った唯一の測定例です。

ニックネーム検出は、明示的な文脈付きの `BETTY → BEATRICE` のケース 1 つを使いました。ローカルは 0.796 秒で完了し、リモートは 1.782 秒でした。どちらも precision 1.0、recall 1.0、証拠の網羅率 1.0 でした。短いニックネームのジョブはローカルに保ち、より大きなペルソナの discovery/compile のコホートは測定したうえで Thunder を検討してください。

### CPU の書き出し

Audacity と M4B は、GPU の仕様から切り捨てるのではなく、Thunder で実行しました。それでもローカルが勝ちました。Audacity は 0.040 秒対 0.063 秒、強化した M4B の再実行は 0.167 秒対 0.247 秒です。Audacity のメンバー／ラベルの構造は完全に一致しました。両方の M4B に AAC の音声と、長さが正のタイトル付きの章がちょうど 2 つ入っていました。バイナリのハッシュが違ったのは、ZIP のタイムスタンプと FFmpeg のバージョンがプラットフォーム固有だからです。

## ケーススタディ：Voice Lab — 段階ごとに測定したコンポーネント

挙げた Voice Lab のコンポーネントは、本番に基づくハッシュ検証済みのフィクスチャを使って、ローカルと同一の A100 80 GB インスタンスで実行しました。Preparer の結果は ASR の段階だけを対象にしており、整列と注釈はベンチマークしていません。

| 段階 | ローカル | A100 Thunder | 品質の比較 |
|---|---:|---:|---|
| Preparer の ASR、36.08 秒の音声 | 11.24 秒 | 21.72 秒 | 同じ 91 語の正規化済み文字起こし。整列の float は異なる |
| 重複除去、2 巻 / 8 サンプル | 10.19 秒 | 19.09 秒 | 同じクラスターと同一の正規の統合内容 |
| LoRA 学習、8 サンプル / 1 epoch | 2.1 秒 | 6.5 秒 | OOM によるスキップはゼロ。両方のアダプターをハッシュで検証 |
| プロファイリング、コールドの Qwen2.5 14B Q6 | 6.936 秒 | 78.689 秒 | 音響の指標は同一。キャスティングの行も両方有効 |
| 命名、衝突する 3 つのケース | 0.0216 秒 | 0.0541 秒 | バイト単位で同一のマニフェストと同じディレクトリー名 |

測定による結論は以前の見積もりより強く、**試験した Voice Lab のコンポーネントは速度のためにローカルに保つ**べきです。リモートのセットアップが面倒だからという理由だけではありません。限られた範囲の LoRA 学習の較正はローカルが 3.10 倍速く、プロファイリングはローカルが 11.35 倍速かったです。転送とプロビジョニングのオーバーヘッドはこれらの計時の結果から除いているので、含めればローカルの推奨はさらに強まります。

これは、将来のすべての大きな学習ジョブがローカルの方が速いと証明するものではありません。GPU の仕様だけではこのスタックの良い予測子にならなかったことを証明しています。はるかに大きなデータセットが 16 GB のカードで OOM するなら、Thunder は容量の逃げ道として残ります。A100 をスループットの向上として扱う前に、その新しいデータセットの形をベンチマークしてください。

UI から起動する本番の Voice Lab のジョブは、ローカル専用のままです。SSH のベンチマークアダプターは較正のインフラであり、本番のリモートジョブのルーティングではありません。容量の逃げ道として Thunder を使うには現在マニュアルの作業が必要で、Voice Lab を Thunder へ自動でディスパッチする仕組みは作られていません。

### プロファイリングの段階別の内訳

コールドのプロファイリングの結果は、2 つの大きく異なるワークロードを合わせたものでした。

| 段階 | RX 9070 XT | A100 Thunder |
|---|---:|---:|
| GGUF モデルの読み込み | 4.246 秒 | 57.344 秒 |
| Librosa の音響 | 1.307 秒 | 16.696 秒 |
| llama.cpp の説明 | 1.381 秒 | 4.642 秒 |

## 7. セットアップの落とし穴（どれも過去に踏んだもの）

- **LM Studio は `0.0.0.0` にバインドする必要があります。** 「running」と表示するリモートの LM Studio でも、`--bind 0.0.0.0` なしでは転送 URL から到達できません。ネットワークのバグに見えますが、違います。
- **SSH の出力には飾りのバナーがあります。** **最後の空でない行**を解析してください。きれいな stdout を前提にしないでください（`lmstudio_settings.get_remote_lmstudio_status` を参照）。
- **複数の文をまとめた SSH は、あらかじめ引用した 1 つの argv 要素でなければなりません** — `"bash -lc " + shlex.quote(cmd)`。`"bash", "-lc", cmd` と分けて渡すと、`ssh` が空白で再結合し、`;` で区切ったコマンドが壊れます。
- **キャッシュされた `concurrency` は古くなります。** モデルやエンドポイントを変えた後は、`llm_remote` のキャッシュされた数値を信じる前に、`concurrency_for` が現在の `base_url::model_name` と一致するか確認してください。
- **ポート転送**は `https://<uuid>-<port>.thundercompute.net` の形に従います。
- **「リモートかどうか」の判断は 1 か所。** `lmstudio_settings.is_remote_llm` を使ってください。決して再導出しないでください（Rule 15。これはすでに実際のずれのバグを起こしました）。
- **CUDA の llama.cpp wheel には NVIDIA のライブラリのパスが必要です。** Thunder は公式の CUDA 12.4 wheel インデックスから `llama-cpp-python==0.3.23` を使いました。最初は直接の import が失敗しました。`libcudart.so.12` がシステムのローダーのパスではなく、Python 環境の `site-packages/nvidia/*/lib` ディレクトリーの下にあったためです。恒久的な `/home/ubuntu/ttsenv/bin/python-cuda` のラッパーがそれらのディレクトリーを見つけ、`LD_LIBRARY_PATH` の先頭に追加してから `/home/ubuntu/ttsenv/bin/python` を実行します。
- **GPU の実際の経路を確認する。import の成功だけでは足りません。** ラッパーは実際の GGUF の推論で試しました。llama.cpp が CUDA を検出し、モデルを A100 にオフロードし、トークンを生成しました。プロファイリングのベンチマークはその後、同じラッパーをエンドツーエンドで使いました。
- **同じモデルのバイトを使う。** プロファイリングの比較は両方のマシンで `Qwen2.5-14B-Instruct-Q6_K.gguf` を使い、SHA-256 は `18cd6b7d5feb00c57ff81ede8f2164ffd86be90dbee9c05bf09ded1ab179740d` でした。Thunder には別の Gemma GGUF もありましたが、公平なプロファイリングの比較の代わりには使いませんでした。
- **M4B には FFmpeg/FFprobe が必要です。** A100 のイメージには FFmpeg が入っていませんでした。書き出しの比較では Ubuntu の FFmpeg 4.4.2 を導入しました。音声をステージした後に気づくのではなく、新しいインスタンスでこの依存をプリフライトしてください。
