# LLM リクエストの予算

**Setup → LLM Settings** では、Local と Remote の各プロファイルに 3 つの任意のトークン上限があります。

| 設定 | 空欄のときの動作 | 効果 |
| --- | --- | --- |
| Total context budget | 検出できれば、読み込み済みのコンテキストを使用 | プロンプト、出力、安全用の余裕を合わせた上限。宣言しても、検出したより小さいコンテキストを大きくすることはできません。 |
| Input ceiling | 任意の Advanced のグローバル入力上限を継承 | 指示、キャスト、周辺テキストを含む、プロンプト全体の推定値の上限。 |
| Output ceiling | プロファイルの上限なし。各タスクが独自の再試行上限を保つ | 設定すると、完了分の許容量と再試行時の引き上げを制限します。プロバイダーが出力に数える場合は推論も含みます。 |

値は正の整数である必要があります。普遍的な上限や、無制限・バイパスの設定はありません。入力上限と出力上限は別々の制約であり、両者の合計が読み込み済みコンテキストに収まる証拠ではありません。たとえば、入力上限と出力上限をそれぞれ 4,096 にしても、4,096 トークンのコンテキストで両方を消費することはできません。

読み込み済みコンテキストが 8,192 で宣言が 4,096 なら、Alexandria は 4,096 を使います。読み込み済みコンテキストが 4,096 で宣言が 8,192 でも、Alexandria は 4,096 を使います。エンドポイントがコンテキストを公開できない場合、宣言が不足する予算を補います。宣言するのは、読み込んだモデルが実際に扱えるコンテキストであり、公称の最大値ではありません。

3 パス処理のソース／コンテキストの目標を大きくするには、検出または宣言したコンテキストが必要です。ない場合、開始リクエストはバックグラウンドジョブを確保する前に、Setup のどの項目を設定すべきかを示します。まだ読み込まれていない管理対象の LM Studio モデルは既知として扱います。実行時に、予定したコンテキストで先に読み込むためです。計画時と実際の HTTP／手動リクエストは同じ上限解決処理を使います。大きすぎるプロンプトは拒否され、出力予算は残りのコンテキストに収まるよう減らされることがあります。既存のソース忠実性チェック、上限付きの再試行、GPU の受け入れ判定は引き続き有効です。

トークン数は既存の保守的な文字数推定を使い、プロバイダー固有のトークナイザーは使いません。サーバー側でのコンテキスト強制は引き続き必要です。小さい予算を宣言するとリクエストが制限されますが、サーバーがすでに確保した VRAM が解放されたり、モデルが再読み込みされたりするわけではありません。

## 既存の構成

プロファイルの上限を設定するまで、既存の構成に変化はありません。Baseline Response Tokens は開始時の予算のままで、上限ではありません。切り捨て時の再試行は、各タスク独自の上限（3 パス処理は 16384、ベースラインがそれより高ければベースライン、レビューは 32768）まで引き上げられるため、推論モデルがベースラインで打ち切られることはありません。モデルに上限を設けるには、プロファイルの Output ceiling を設定します。コンテキストの合計チェックは引き続き適用されます。

既存の構成に新しいグローバル入力上限は課されません。未設定または空欄なら、コンテキストに基づく検査が維持されます。プロファイルの入力上限が空欄の場合、保存したプロファイル設定を変えずに、実行時にグローバル設定を継承します。手動での受け渡しでも、コピー用にリクエストを提示する前に同じ宣言済みの上限を強制します。フェイルオーバーでは、プライマリーモデルの予算まで広げるのではなく、セカンダリープロファイルの上限を使います。
