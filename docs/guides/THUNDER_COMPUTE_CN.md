# 什么时候用 Thunder Compute（以及用来做什么）

一份给本项目用的决策指南。**默认在本地跑**——Thunder 是例外，不是基线。

你的硬件：**AMD Radeon RX 9070 XT**（16 GB，RDNA4/ROCm），在 `localhost:1234` 上跑 LM Studio。应用默认 `llm_mode: local`；也可以配置一个 Thunder 远程配置档。在假定没有任何东西在计费之前，永远先看 `tnr status`。

---

## 1. 一条规则

> 当任务**在本地根本跑不起来**，或者本地要跑太久、以至于实际耗时比钱更要紧时，才用 Thunder。
> 其他一切情况：留在本地。

**A6000 每小时 $0.35**（价格查于 2026-07-18）的情况下，干了几个小时之后成本很少是决定因素。决定因素是**显存**、**CUDA** 和**实际耗时**。

---

## 2. 以下情况用 Thunder

| 原因 | 为什么本地不行 | 建议的 GPU |
|---|---|---|
| **模型需要 > 16 GB 显存** | 9070 XT 最多给你约 16 GB。更大的模型或更长的上下文装不下。 | A6000 (48 GB)，$0.35/hr |
| **只支持 CUDA 的代码** | 你的卡是 ROCm。任何假定有 CUDA kernel 的东西（某些 `xformers`/`triton`/`sageattention`/`flash-attn` 构建，以及大多数上游 ML 轮子）都跑不了。 | A6000 / L40 |
| **你需要把桌面拿回来** | 本地 LLM 工作会占住显卡；全局 GPU 锁会挡住应用里其他所有任务。 | A6000 |
| **用测过的 Gemma 端点做人设生成** | A100 完成生产级的发现/编译批次快了 2.27 倍。 | A100 80 GB |
| **某个负载在本地确实 OOM 过** | 实测下来 A100 在所有测过的 TTS 和 Voice Lab 阶段上都更慢，包括 LoRA 训练。只有在容量、而不是你以为的速度是瓶颈时才用它。 | 按观察到的显存需求来选 |

## 3. 以下情况不要用 Thunder

- **纯 CPU 的工作。** Audacity、M4B 和 Voice Lab 命名在两台机器上都测过；三次本地都更快。
- **很短或交互式的任务。** 准备开销（创建 → SSH → 加载模型 → 端口转发）远大于几分钟的推理。
- **追求并行度。** 见第 4 节——这是最关键的一条。
- **任何你还没确认是真的受 GPU 限制的事。** 先检查；不要为了修一个 I/O 或 LLM 延迟问题去租 GPU。

---

## 4. Thunder 买到的是显存和 CUDA——速度必须实测

这是实测的，不是理论，而且是这里最反直觉的一点：

> 在一次历史上的 Thunder **A6000** 运行中（原始报告没有入库版本），
> `concurrency`/`parallel` **> 1 的审阅比 1 更慢**——而且**在 4 时崩溃**。
> 把并发保持在 **1**。不要自动放大 `parallel`。

本地这边，`lmstudio_settings.IDEAL_SETTINGS` 出于显存安全故意把 `parallel: 1` 钉住——这是有意的取舍（规则 9），不是靠租 GPU 去"修"的 bug。所以走远程**并不会**解锁并发请求。如果你租一台 A6000 指望靠并行拿到 4 倍吞吐，你会付 4 倍的钱，拿到不到 1 倍的效果。

租 Thunder 是为了**显存余量和 CUDA**。不要在没有实测确切模型/运行时的情况下，假定每 token 速度或扇出会改善。

瓶颈取决于完整的软件路径，而不只是显卡规格。A100 输掉了实测的 LoRA 训练校准，尽管训练本身是计算密集的。基准测试没有剖析原因；可能的因素包括准备、数据、小批量、kernel 和框架开销。在没有一个生产形态的测量之前，不要把理论上的算力优势上升为部署规则。

### 本次评测已知的混杂因素

事后发现，本次评测自己的测试框架里有四个缺口。它们都不意味着下面的数字是编造的，但这次评测对它们也都没有做控制——在重跑解决它们之前，把这一节的每个结论都当作暂定的。脚本生成和脚本审阅（两个目标）已在修好的框架下重跑——见前两条下面各自附的验证说明；另外两条（利用率采样、规模化吞吐）仍然适用于本文档里所有 TTS/LoRA/VoiceLab 数字，那些还没有重跑。

- **Torch/CUDA 构建不匹配。** 本地跑 Torch 2.10.0+ROCm7.0；Thunder 跑的是更旧的 Torch 2.7.0+CUDA12.6。下面每一个 TTS/LoRA/VoiceLab 对比都是在两套不同的软件栈之间测的，不只是两块 GPU 之间。基准框架现在会记录双方 Torch 版本的指纹，并在同一次预检里两边都采集到而版本不一致时大声报错（`benchmark_environment.verify_comparable_environments`）。**2026-07-18 已核验：** Thunder 的 Torch 已就地升级到 2.10.0+CUDA12.6（与本地的主版本一致；torchaudio/triton/CUDA 依赖同步更新，transformers/peft/qwen_tts 未动且重新 import 正常），脚本生成/复核重跑的预检也干净通过。TTS/LoRA/VoiceLab 各阶段还没有在版本对齐后的 Torch 上重跑。
- **NVIDIA 上原本没有利用率埋点。** 下面 CustomVoice 部分那句"A100 只跑到约 15% 利用率"是一次临时的、没有重复的观察——`gpu_stats.py` 只有给 AMD 用的 `rocm_smi_utilization`。`tts_benchmark.py` 现在会在每次生成调用期间通过新的 `gpu_stats.sample_gpu_utilization()`（NVIDIA 或 AMD，哪个在就采哪个）采样 `mean_gpu_utilization_pct`，所以以后的运行能拿到真正的指标，而不是靠眼睛估的附注。还没有在真实的 TTS 硬件上跑过——这次验证只重跑了基于 LLM 的阶段。
- **基于 LLM 的基准测到了网络往返，不只是解码。** 脚本生成/复核、人设和昵称检测过去都是由本地编排器直接调用配置好的 LM Studio 端点；对 "thunder" 目标来说，这等于把一次穿过 SSH 转发 HTTPS 隧道的互联网往返烤进了每一次 fixture×repetition 调用里，而不是只发生一次。这在昵称检测那种不到 2 秒的总时长里最明显，一次 RTT 就能让报出来的时间翻倍。第一步缓解（2026-07-18）：每个 LLM 阶段运行器每份报告记录一次 `network_rtt_seconds` 基线探测——脚本生成/复核实测本地 0.083 秒，Thunder 0.53–0.54 秒（约 6.5 倍），证实这个混杂确实存在。但那只是**测量**混杂，所以真正的修复随后才到：`llm_benchmark_worker.py` 现在通过 SSH **在** Thunder 主机上跑整个循环（照搬 TTS/LoRA/VoiceLab worker 的模式——先放到远端，再在远端跑，从那里访问 `localhost`，而不是走公开的转发 URL），这样网络只在启动一批任务的那一次 SSH 往返上有影响，而不是每次 LLM 调用都有。只要一个 manifest 设置了 `settings.remote_root`/`remote_python`，4 个 LLM 阶段都可用，和 TTS 家族各阶段一样。还没有在真实硬件上跑过（落地时没有活的 Thunder 实例）——只用 mock 过的 SSH 做了单元测试。
- **每一个 TTS/LoRA/VoiceLab 基准都是单流或小批量的**（串行的六次生成、下面的批上限 ≤16）——这正是 A100 最弱、消费级显卡最强的形态。这里没有任何东西测过数据中心 GPU 生来擅长的规模吞吐区间。现有的 `tts_vram_benchmark.py --sizes 32 64`（它的 `--sizes` 参数本来就接受任意上限列表——不用改代码）还没有在这些更大的上限下于 Thunder 上跑过；这是建议的下一个实验：在确认"本地赢下 TTS"对每个批大小都成立（而不只是 ≤16）之前，先不要把它当成普遍结论。

**归档约定：** 本次评测的 13 个阶段里，只有 2 个在需要再次用到时还留着原始的 `reports/benchmarks/<preflight_id>.json`——另外 11 个在数字被抄进本文档之后就被清掉了，所以重建它们确切的 fixture 花了不少工夫。往后，在一个阶段的临时副本被删掉之前，先把它的报告归档到 [`../benchmarks/raw/`](../benchmarks/raw/)（入库跟踪，见它的 `README.md`），这样以后任何阶段的数字都能重新核验或重跑，而不必从头再做 fixture 选型。

### A100 脚本生成基准——2026-07-18

这是一个小的受控批组，不是通用的 GPU 排名。两台机器都用同一个 Gemma 4 E4B Q8 模型、三个历史上的约 6,000 字符分块、每个重复三次，以及 `max_retries: 0`。零重试测的是原始的单次尝试可靠性，不是生产的完成率。

| 环境 | 通过 | 总时间 | 成功调用均值 | 聚合完成速率 |
|---|---:|---:|---:|---:|
| RX 9070 XT，32,768 上下文，parallel 2 | 7/9 | 329.5 s | 43.9 s | 65.5 tok/s |
| A100 80 GB，98,304 上下文，parallel 2 | 7/9 | 679.4 s | 94.9 s | 32.9 tok/s |
| A100 80 GB，32,768 上下文，parallel 2 | 6/9 | 1,032.7 s | 105.3 s | 20.6 tok/s |

失败大多是随机性的提前停止或结构上无效的输出；质量门正确地拒绝了不完整的脚本。降低 Thunder 的上下文**并没有**修好它的单流速度，所以 98k 的 KV 分配不是被证明的瓶颈。

在 32,768 上下文下做的一次生产形态的三轮并发扫描发现：

| LM Studio parallel / 同时请求数 | 聚合完成速率中位数 |
|---|---:|
| 1 / 1 | 43.5 tok/s |
| 2 / 2 | 17.9 tok/s |

parallel 2 慢了 59%，所以安全策略在测到 4/8/16 之前就停了。对这个确切的 A100/Gemma/LM Studio 组合，**parallel 1 是实测的最优值**。实用建议是让 Gemma 脚本生成留在本地的 RX 9070 XT 上；只有显存/CUDA 或另一个实测过的负载能证明其必要时才用这台 A100。不要把这些解码结果外推到 TTS、训练或 Voice Lab；它们各自独立的实测结果记录在下面。

当前受保护的 `REMOTE_IDEAL_SETTINGS` 仍然配置为 `parallel: 2`，远程自愈还可能把这个值恢复回去。在有意改动并验证这个安全敏感的生产设置之前，parallel-1 的实测结果只是建议性的；本指南不会悄悄覆盖它。

### A100 脚本复核基准——2026-07-18

生产的 `review_batch` 路径在第 3、9、10 卷的三批不可变 25 条目上做了测量，三次重复，零重试。两个环境用同一个模型和 32,768 上下文；Thunder 用它实测的 parallel-1 最优值，本地保持它的 parallel-2 配置。

| 环境 | 通过 | 总时间 | 批均值 | 聚合完成速率 | 词数比均值 |
|---|---:|---:|---:|---:|---:|
| RX 9070 XT 本地 | 9/9 | 238.3 s | 26.5 s | 63.9 tok/s | 0.9993 |
| A100 80 GB Thunder | 9/9 | 474.3 s | 52.7 s | 32.0 tok/s | 0.9978 |

两者都保持了结构，并且都落在生产 95–105% 文本丢失门之内。Thunder 在这个批组里没有带来任何可靠性优势，而且几乎正好慢 2 倍。对这个模型/运行时，**把 Gemma 脚本复核留在本地**。这强化了脚本生成的结果，但仍然说明不了 LoRA 训练的表现。

### A100 CustomVoice TTS 基准——2026-07-18

生产的 `TTSEngine.generate_custom_voice` 路径用同样三个短/中/长叙述 fixture、固定种子、1,024 生成 token 上限、每个 fixture 两次重复来测量。模型加载和生成分别计时。两个环境都没有 `flash-attn`，都用 PyTorch 手动注意力路径；本地用 Torch 2.10.0+ROCm 7.0，Thunder 用 Torch 2.7.0+CUDA 12.6。两台机器上 LM Studio 都常驻。

| 环境 | 通过 | 缓存模型加载 | 预热音频吞吐 | 削波输出 |
|---|---:|---:|---:|---:|
| RX 9070 XT 本地 | 6/6 | 6.2 s | 1.18 音频秒/墙上秒 | 0/6 |
| A100 80 GB Thunder | 6/6 | 21.8 s | 0.28 音频秒/墙上秒 | 0/6 |

固定种子在每台机器的各次重复之间产生完全相同的哈希；跨后端的哈希和时长略有差异，这在 Torch/GPU kernel 不同的情况下是意料之中的。所有 WAV 都是有效的 24 kHz 单声道 PCM，非静音，未削波。

对这个确切的串行 CustomVoice 路径，本地 RX 9070 XT 每墙上秒产出的音频约多 **4.2 倍**，而且本来就已经快于实时；观察期间 A100 只跑到约 15% 利用率。所以 A100 的大显存并没有转化成单流速度。在这个软件栈下，把串行 CustomVoice 生成留在本地。原生列表批处理在下面单独测量。LoRA 训练仍是一个单独的批组，所以那个结果也在下面单独测。

#### CustomVoice 原生批处理容量

生产的 `_local_batch_custom` 路径在每台机器上用 16 个完全相同的、长度混合的源分块做了扫描。上限高于 8 没有帮助：在 16 时，长度比拆分仍然产生两个子批次，而自回归填充降低了吞吐。最初的容量扫描发现：

| 批上限 | RX 9070 XT 实时倍率 | A100 实时倍率 | A100 失败数 |
|---:|---:|---:|---:|
| 2 | 1.71× | 0.47× | 0/16 |
| 4 | 3.12× | 0.86× | 0/16 |
| 8 | 4.93× | 1.32× | 0/16 |
| 16 | 4.03× | 0.89× | 0/16 |

那次扫描暴露了两个测量缺陷：工具只报了最后一个子批次的显存峰值，而且没有固定 TTS 种子。两者都在确认运行之前修正了。用 `batch_seed=42` 和上限 8，本地在 **87.3s** 内以 9.64 GB 峰值完成了全部 16 个输入；A100 在 **210.6s** 内以 10.12 GB 峰值完成。即使种子相同，输出时长在 ROCm/CUDA kernel 之间也会不同，所以等输入下的实际耗时才是主要比较依据：本地快 **2.41 倍**。实测的最优值在两台机器上都是上限 8；对这类长度混合的负载，A100 的容量并没有允许超出它有意义的扩展。

#### 基座模型声音克隆

生产的克隆路径在两台机器上使用同一个经哈希核验的 Watson 参考音频和转写。三段短/中/长目标文本用固定种子和 1,024 token 上限各跑两次。模型加载、可复用克隆提示词构建和生成分别计时。

| 环境 | 通过 | Base 加载 | 提示词构建 | 六次生成 | 聚合音频吞吐 |
|---|---:|---:|---:|---:|---:|
| RX 9070 XT 本地 | 6/6 | 6.44 s | 0.99 s | 44.8 s | 1.15× 实时 |
| A100 80 GB Thunder | 6/6 | 30.14 s | 7.20 s | 228.3 s | 0.25× 实时 |

所有输出都是有效的 24 kHz 单声道 PCM，在每个后端内确定性一致，非静音，未削波。对相同的目标输入，本地生成快 **5.09 倍**。在这些 Torch/Qwen 栈下，把串行 Base 模型克隆留在本地。

随后用和 CustomVoice 相同的 16 个确定性混合长度输入扫描了原生克隆批处理路径：

| 批上限 | RX 9070 XT 时间 / 实时倍率 / 峰值 | A100 时间 / 实时倍率 / 峰值 |
|---:|---:|---:|
| 2 | 80.5 s / 1.91× / 6.13 GB | 322.3 s / 0.47× / 5.72 GB |
| 4 | 45.5 s / 3.45× / 7.17 GB | 183.7 s / 0.84× / 7.21 GB |
| 8 | **37.3 s / 4.27× / 9.25 GB** | **107.8 s / 1.43× / 10.17 GB** |
| 16 | 40.1 s / 3.88× / 11.84 GB | 153.5 s / 1.02× / 13.87 GB |

两台机器、四个上限下的全部 128 个输出都成功完成。上限 8 是两块 GPU 上实测的最优值。在这个共同的最优点上，按等输入实际耗时算本地快 **2.89 倍**。上限 16 出现了回退，因为最后三个长分块组成了更慢的第二个子批次；A100 当时还有大约 67 GB 没用，所以额外的容量并不是答案。

#### VoiceDesign 预览

生产的 `generate_voice_design` 调用用三段不同的声音描述和短/中/长目标文本、每段两次固定种子重复、1,024 token 上限来测量。基准包含真实的预览 WAV 创建，并把那个文件移进基准输出目录。

| 环境 | 通过 | 缓存模型加载 | 六次生成 | 聚合音频吞吐 |
|---|---:|---:|---:|---:|
| RX 9070 XT 本地 | 6/6 | 6.07 s | 40.7 s | 1.15× 实时 |
| A100 80 GB Thunder | 6/6 | 24.21 s | 173.9 s | 0.27× 实时 |

按等输入实际耗时算，本地 VoiceDesign 生成快 **4.27 倍**。所有输出都有效、非静音、未削波。本地的重复是逐位相同的。A100 的一次中等重复尽管种子固定，仍有极小的采样级差异，而它的时长和健康指标实际上完全相同；不要把 CUDA 的 VoiceDesign 输出当成保证逐位确定的。在这些软件栈下，把 VoiceDesign 预览和设计声音的分块生成留在本地。

#### LoRA TTS 推理

生产的 LoRA 路径在两台机器上使用同一个经哈希核验的 Watson 适配器、种子和提示词。它分别测量了模型/适配器加载、可复用提示词构建和预热生成。

| 阶段 | RX 9070 XT | A100 Thunder |
|---|---:|---:|
| 模型 + 适配器加载 | 4.54 s | 23.43 s |
| 提示词构建 | 0.86 s | 7.02 s |
| 预热生成 | 5.48 s | 32.05 s |

本地预热生成快 **5.85 倍**。两个环境在各次重复中都产出了健康、确定性的输出。在这个适配器/模型栈下，把 LoRA 推理留在本地。

### 人设与昵称 LLM 工具

高级人设基准故意只测到预览边界，而不再次生成 TTS。每个目标在同一个双说话人 fixture 上执行一次发现调用和两次编译调用。Thunder 用 17.557 秒，本地 39.885 秒：**Thunder 快 2.27 倍**，并且两边都是 100% 的说话人和证据覆盖。这是 A100 唯一一次实测赢下的实际耗时。

昵称检测用了一个显式的上下文 `BETTY → BEATRICE` 案例。本地 0.796 秒，远程 1.782 秒。两边都达到精确率 1.0、召回 1.0、证据覆盖 1.0。短的昵称任务留在本地；更大规模的人设发现/编译批组可以在实测之后考虑 Thunder。

### CPU 导出

Audacity 和 M4B 是在 Thunder 上跑的，而不是凭显卡规格就把它排除掉。本地仍然赢：Audacity 0.040 秒对 0.063 秒，强化后的 M4B 重跑 0.167 秒对 0.247 秒。Audacity 的成员/标签结构完全一致。两个 M4B 都含 AAC 音频，并且都正好有两个时长为正、带标题的章节。二进制哈希不同，因为 ZIP 时间戳和 FFmpeg 版本与平台相关。

## 案例研究：Voice Lab——按阶段测量的组件

列出的 Voice Lab 组件分别在本地和同一台 A100 80 GB 实例上运行，使用生产支撑的、经哈希核验的 fixture。Preparer 的结果只覆盖它的 ASR 阶段；对齐和标注没有做基准测试。

| 阶段 | 本地 | A100 Thunder | 质量对比 |
|---|---:|---:|---|
| Preparer ASR，36.08 秒音频 | 11.24 s | 21.72 s | 同样 91 词的归一化转写；对齐浮点数有差异 |
| 去重，两卷 / 8 个样本 | 10.19 s | 19.09 s | 相同的聚类，规范合并内容完全一致 |
| LoRA 训练，8 个样本 / 1 个 epoch | 2.1 s | 6.5 s | 零 OOM 跳过；两个适配器都经哈希核验 |
| 画像，冷启动 Qwen2.5 14B Q6 | 6.936 s | 78.689 s | 声学指标完全相同；两条选角台词都有效 |

从 UI 启动的生产 Voice Lab 任务仍然只在本地。那些 SSH 基准适配器是校准基础设施，不是生产的远程任务路由。目前把 Thunder 当容量逃生口还需要手工流程；自动把 Voice Lab 派发到 Thunder 的能力还没有实现。

## 7. 配置的坑（每一个都咬过人）

- **LM Studio 必须绑定 `0.0.0.0`。** 一个报着 "running" 的远程 LM Studio，没有 `--bind 0.0.0.0` 时通过转发 URL 仍然访问不到。看起来像网络 bug，其实不是。
- **SSH 输出前面有装饰性横幅。** 解析**最后一个非空行**；绝不要假定 stdout 是干净的（见 `lmstudio_settings.get_remote_lmstudio_status`）。
- **多语句 SSH 必须是一个预先加好引号的 argv 元素**——`"bash -lc " + shlex.quote(cmd)`。把 `"bash", "-lc", cmd` 分开传，`ssh` 会用裸空格把它们重新拼起来，从而破坏 `;` 分隔的命令。
- **缓存的 `concurrency` 会过期。** 换模型或端点之后，先确认 `concurrency_for` 和当前的 `base_url::model_name` 匹配，再去相信 `llm_remote` 里缓存的那个数字。
- **端口转发**走 `https://<uuid>-<port>.thundercompute.net`。
- **"是不是远程"只有一个来源。** 用 `lmstudio_settings.is_remote_llm`——绝不要另行推导（规则 15；这已经造成过一个真实的漂移 bug）。
- **CUDA 版 llama.cpp 轮子需要 NVIDIA 的库路径。** Thunder 用的是官方 CUDA 12.4 轮子索引里的 `llama-cpp-python==0.3.23`。直接 import 它一开始会失败，因为 `libcudart.so.12` 在 Python 环境的 `site-packages/nvidia/*/lib` 目录里，而不在系统加载器路径上。常驻的 `/home/ubuntu/ttsenv/bin/python-cuda` 包装脚本会找出这些目录，把它们前置到 `LD_LIBRARY_PATH`，然后执行 `/home/ubuntu/ttsenv/bin/python`。
- **核实实际的 GPU 路径，而不只是 import 成功。** 那个包装脚本用真实的 GGUF 推理测过：llama.cpp 检测到 CUDA，把模型卸载到 A100，并生成了 token。之后画像基准端到端地用了同一个包装脚本。
- **使用相同的模型字节。** 画像对比在两台机器上都用 `Qwen2.5-14B-Instruct-Q6_K.gguf`，SHA-256 为 `18cd6b7d5feb00c57ff81ede8f2164ffd86be90dbee9c05bf09ded1ab179740d`。Thunder 上还有一个不同的 Gemma GGUF；为了画像对比的公平性，没有用它替换。
- **M4B 需要 FFmpeg/FFprobe。** A100 的镜像里没有 FFmpeg。导出对比时装了 Ubuntu FFmpeg 4.4.2。请在全新的实例上预先检查这个依赖，而不是在传完音频之后才发现。
