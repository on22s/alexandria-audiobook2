# 話者判定用アダプターを有効にする

アダプターが存在する理由は今では 1 つです。**より小さい量子化で出荷できるようにするため。** ベースモデルではプロンプト（`michel2_full`）が精度を担っていました。アダプターは、効果があると測定された段階でのみ読み込む価値があります。すべての行は、公開コレクション [Om22s/alexandria-qwen3-attribution](https://huggingface.co/Om22s/alexandria-qwen3-attribution) の 4 冊の製品フィクスチャ（768 行、1 つのサーバーでアダプターの scale を切り替えてベース → アダプターを対にした比較、temperature 0、JSON schema、`michel2_full`）によるものです（RECIPES §「Attribution adapters」、2026-09-20）。

| ベース | 段（ファイル） | 推論 | ベース → アダプター | 読み込むか |
| --- | --- | --- | ---: | --- |
| Qwen3.8-27B | IQ2_XXS (7.3 GB) | on | 83.1 → **85.7 (+2.6)** | **はい** — このアダプターのための段階 |
| Qwen3.8-27B | Q3_K_XL (13.1 GB) | on | 87.5 → **88.8 (+1.3)** | はい |
| Qwen3.8-27B | Q4_K_M (16.5 GB) | on / off | 89.8 → 89.8 (0) / 87.4 → 88.3 (+0.9) | 推論ありならいいえ。推論なしならわずか |
| Qwen3.6-35B-A3B | IQ1_M (10.0 GB) | off | 82.9 → **85.9 (+3.0)** | **はい、推論オフのときだけ** |
| Qwen3.6-35B-A3B | IQ1_M | on | 87.5 → 85.0 (−2.5) | いいえ |
| Qwen3.6-35B-A3B | IQ2_XXS (10.8 GB) | on | 88.3 → 87.9 (−0.4) | いいえ |
| Qwen3.6-35B-A3B | IQ3_XXS (13.2 GB) | on | 87.5 → 86.6 (−0.9) | いいえ |
| Qwen3.6-35B-A3B | Q4_K_XL (22.4 GB) | on | 90.8 → 88.5 (−2.2) | いいえ |
| Qwen3-14B | Q4_K_M (9.0 GB) | low、budget 1024 | `default` では 66.1 → **74.7 / 74.9 (+8.6 / +8.8)**、PDNC の 9 冊で `michel2_full` では **84.3 → 84.3 (0)** | `default` プロンプトのときだけ。`michel2_full` ではベースを使う |

この表だけでは分からないことが 2 つあります。PDNC のテキスト（別名を含む人物一覧）で A3B アダプターを使うと、人物一覧の行をそのままコピーして返すことが最大 12% の行で起こります（`EMMA (also: EMMA WOODHOUSE, …)`）。#625 以降、アプリはこれを `EMMA` として読みますが、ハーネスは誤って採点するため、アダプター自身のカードには両方の数値が載っています。また、Qwen3-14B の改善はプロンプト固有です。`default` の形で学習されており、製品のプロンプトでは効果がありません。

## アプリケーションではなく、サービングの変更

アダプターは `llama-server` が適用します。`app/` の中では何も計算に使いません。

```bash
llama-server \
  -m /path/to/Qwen3.8-27B-UD-IQ2_XXS.gguf \
  --lora /path/to/qwen38-rightsclean-michel2.f16.gguf \
  --host 127.0.0.1 --port 8090 -c 32768 --parallel 1
```

コレクションの各 `adapters/<name>/` ディレクトリーにある `.f16.gguf` が、測定に使ったファイルです（そこの `examples/serve_llamacpp.sh` が上のコマンドを実行します）。このページの以前の版で説明していた、ライトノベルで学習した `adapter_mixed.gguf` は配布できず、非公開のアーカイブに残っています。

次に、実行しているモードのブロック内で、`app/config.json` からアプリをそのアダプターに向けます。

```json
"llm_local": {
  "base_url": "http://127.0.0.1:8090/v1",
  "model_name": "qwen3.8-27b",
  "attribution_adapter": {
    "path": "models/qwen38-rightsclean-michel2.f16.gguf",
    "scale": 1.0,
    "require": false
  }
}
```

アダプターを `base_url` と同じブロックに置くのは意図的です。そのエンドポイントに属するものであり、別の場所に置くと、どちらのサーバーを指すかで食い違う可能性があるためです。

## このチェックが行うこと

`generate_script.py` は起動時に次を表示します。

```
LLM adapter: attribution_adapter=qwen38-rightsclean-michel2.f16.gguf scale=1.0 require=False
```

さらに、サーバーが実際にはそれを提供していない場合に警告します。**これがこの仕組み全体の要点です。** これがないと、`--lora` なしで起動したサーバーや、scale を 0 に切り替えたサーバーが、ベース品質で何事もなくすべてのリクエストに答えてしまいます。何も失敗しません。本は生成されます。ただそれはベースの数値であり、なぜそうなったかを記録する成果物もありません。seed のバグと同じ形で、誰かが耳で気づくまで 6 回の汚染された比較を費やしました。

`require: true` にすると、警告は拒否になります。既定で警告にとどめるのは、夜間に半分生成した本が、サーバーの再起動で失われないようにするためです。ただし、実行はその事実を記録している必要があります。

## 正直な 3 つの限界

**エンドポイントは llama.cpp でなければなりません。** LM Studio と Ollama は `/lora-adapters` を実装していないため、チェックはアダプターがないふりをせず「cannot verify」と報告します。これは意図的です。どの構成でも鳴る警告は、誰も読まない警告です。

**scale は調整していません。** 1.0 は評価で使った値です。`POST /lora-adapters` で任意の値に設定できますが、0.7 や 1.3 がより良いかはここでは何も測定していません。

**改善はライトノベルと、PDNC の 2 冊で測定しています。** 4 冊のゴールドの本は英語に翻訳された日本のライトノベルです。PDNC の 2 冊分のセル（Emma はホールドアウト、The Sun Also Rises は学習に使った本）はカードに載っています。学習データは英語のパブリックドメインの散文なので、ライトノベルでの改善は転移によるもので、小さなものです。
