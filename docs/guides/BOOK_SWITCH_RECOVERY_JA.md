# 中断した本の保存と切り替え

保存済みの本を読み込むとき、または現在の本を保存するときは、台本、声の設定、章ファイルなど複数のファイルを一度に置き換えます。アプリはこれをジャーナル付きのトランザクションとして行うため、クラッシュ、電源断、ディスク容量不足でも本が半分だけ新しい状態になることはありません。このガイドでは、中断後に何が起きるか、アプリだけでは完了できないときにどうするかを説明します。

## 自動で行われること

本を読む、または変更するすべての操作の前に、アプリは中断された切り替えを探します。データフォルダー内の `.active_book_transaction.json` というジャーナルと、その隣の作業フォルダー `.book-switch-<id>/` です。（Home ページの状態表示だけは例外で、復旧を行わないため、`finish` で完了できる切り替えを表示することがあります。）

- **復旧は切り替えを完了またはロールバックします**。すべてのファイルがジャーナルの記録どおりの場所にあり、記録されたバイト内容と一致する場合です。通常はこのケースで、何も表示されません。
- **自動隔離**は、すべての本のファイルがジャーナルと一致しているのに、作業フォルダーが一致しない場合に行われます。ステージングされたファイルが変わった、未知のファイルが現れた、またはクリーンアップが途中で止まった場合です。作業フォルダーとジャーナルは `.book-switch-quarantine-<journal hash>-<nonce>/` に移動され、本は開きます。何も削除されません。
- **それ以外は切り替えが拒否され**、本は開きません。本のファイル自体が変わった、フォルダーが入れ替わった、またはジャーナルが壊れている場合です。アプリはどちらのバージョンが正しいかを推測しません。

本がこの理由で開けないとき、Home ページは以下を試す順に表示します。`inspect`、次に `finish`、`finish` が拒否した場合にのみ `quarantine --accept-current-files` です。

## クラッシュによる残骸

クラッシュは、どのジャーナルにも属さない 2 種類のものを残すことがあります。

- `.book-switch-<id>/`：ジャーナルが公開される前に終了した切り替えの作業フォルダー。本の完全なステージングコピーを含むことがあります。
- `.active_book_transaction.json.new-<id>`：書き込まれたものの、ジャーナルにならなかったジャーナル公開用の一時ファイル。

`inspect` はこれらを `orphaned_staging` と `journal_temporaries` として、エントリ数、バイト数、最新タイムスタンプとともに一覧表示します。復旧サマリーは件数と合計バイト数（`leftovers`）だけを報告し、名前やパスは決して報告しません。また、アプリがビジーな間は `leftovers: null` を報告します（アプリが今ステージングしている可能性があるため）。似ているだけの名前、リンク、または保留中のジャーナル自体が指定する作業フォルダーは、孤立として報告されません。

アプリはこれらの残骸を決して削除しません。ジャーナルより前のフォルダーには、それが自分たちのものだという証拠がないため、回収するかどうかはあなたの判断です。本が開けることと、そのフォルダーが実行中の切り替えでないことを確認したら、退避フォルダーと同様に自分で削除してください。`inspect --no-lock` は、実際には実行中の切り替えのステージングであるエントリを表示することがあります。削除する前にロック下で `inspect` を再実行してください。

## クラッシュが残すもの

切り替えは本のファイルを決まった順序で変更します。Linux と macOS（ファイルシステムが 1 ステップで 2 つの名前を交換できる場合、"v4" ジャーナル）では：

1. すべての新しいファイルをプライベートな `.book-switch-<id>/` フォルダーにステージングし、
2. ジャーナル `.active_book_transaction.json` を書き込み（フェーズ `publishing`）、
3. ステージングしたファイルを 1 つずつ所定の場所に交換し、
4. ジャーナルを `committed` にし、
5. ステージングフォルダーを削除し、その後ジャーナルを削除します。

すべての本の操作は最初に復旧を実行します（`app/book_state_transaction.py` の `recover_book_state_locked`）。以下は各時点でクラッシュした後に見えるものと、次に本を開いたときに起きることです。角括弧内はそのケースを処理する関数です。

**ジャーナルができる前（ステップ 1 または 2 の途中）。**
- ディスク上：`.book-switch-<id>/` フォルダー、および書きかけの `.active_book_transaction.json.new-<id>` があるかもしれません。本のファイルはすべて未変更です。
- 次に開くとき：取り消すものが何もないため、本はそのまま開きます。`inspect` はフォルダーを `orphaned_staging` に、書きかけのファイルを `journal_temporaries` に一覧表示し、Home ページはその件数とサイズを表示します。何も自動では削除されません。[`recover_book_state_locked`, `_get_leftover_staging_entries`]
- 必要な操作：切り替えが動いていないことを確認したら、容量を戻したい場合に手動で削除します。

**ジャーナルの後、ファイルを 1 つも交換する前。**
- ディスク上：ジャーナルは `publishing` で、本のファイルはすべてまだ旧版です。
- 次に開くとき：各ファイルをジャーナルと照合し、ステージングフォルダーとジャーナルを削除して、本は未変更のまま開きます。[`_recover_book_exchange_journal`]
- 必要な操作：何もしません。

**交換の途中（ステップ 3）。**
- ディスク上：新しいファイルと古いファイルが混在します。交換済みの各ファイルの旧版（新規作成のファイルなら 64 バイトのプレースホルダー）がステージングフォルダーにあります。作成中のファイルは、本来の名前の位置にそのプレースホルダーを一時的に見せることがあります。
- 次に開くとき：両側を再度確認したうえで、交換済みの各ファイルを交換し戻し、本は切り替え前とまったく同じ状態に戻ります。切り替えが作成中だったファイルは再び消えます。[`_recover_book_exchange_journal`, `_undo_book_exchange`]
- 必要な操作：何もしません。

**すべてのファイルを交換したが、ジャーナルがまだ `committed` でない。**
- ディスク上：本のファイルはすべて新しく、ステージングフォルダーに旧版があります。
- 次に開くとき：前のケースと同じに扱います。`committed` が書かれるまで切り替えの完了は約束されていないため、切り替えはロールバックされ、本は旧ファイルで開きます。唯一の例外は、ジャーナルのすべての行が置き換えで、各ファイルが新しい内容を証明でき、復元すべき旧コピーが残っていない場合で、これは新しいファイルのまま完了します。完了済みと未完了のファイルが混在し、復元できない場合は、半分だけ新しい本として開かずに拒否します。[`_recover_book_exchange_journal`]
- 必要な操作：拒否されない限り何もしません（「cannot be completed consistently」）。拒否されたら `inspect` を実行し、`quarantine --accept-current-files` で現在のファイルを保持します。

**`committed` の後、クリーンアップ中（ステップ 5）。**
- ディスク上：ジャーナルは `committed`、本のファイルはすべて新しく、ステージングフォルダーの一部が残っている場合があります。
- 次に開くとき：各本のファイルを新しい内容と照合したうえで、切り替え自身が作成したものだけを削除し、ジャーナルを削除します。ステージングフォルダー内で自分たちのものと証明できないものは、ジャーナルとともに `.book-switch-quarantine-<hash>-<nonce>/` に移動され、本は新しいファイルのまま開きます。[`_recover_book_exchange_journal`, `_quarantine_book_transaction`]
- 必要な操作：何もしません。証拠が不要になったら隔離フォルダーを削除してください。

**隔離の途中（`receipt.json` がまだ `prepared`）。**
- ディスク上：隔離フォルダーがあり、ステージングフォルダーとジャーナルはそこへ移動済みか、本のルートにまだあります。
- 次に開くとき：ジャーナルがまだルートにあれば隔離を完了しますが、すべてが受領書の記録と一致している場合に限ります。一致しなければ復旧は拒否し、すべてを保持します。ジャーナルがすでに移動済みなら本は開き、移動したジャーナルのサイズとハッシュ、および移動したステージングフォルダーの同一性を再確認したうえで、受領書を `completed` にします。この確認に失敗した受領書は `prepared` のままで、何も移動しません。[`_quarantine_book_transaction`, `_complete_interrupted_quarantines`]
- 必要な操作：通常は何もしません。`prepared` のままの受領書は何かが変わった証拠で、`inspect` に表示されます。

**切り替えの実行中に別のプログラムが本のファイルを変更した。**
ジャーナル以降のどの段階でも、本のファイルが切り替えの旧版でも新版でもない場合、復旧は拒否します。自分が書いていないファイルを交換、削除、退避することはありません。本は閉じたままで、`inspect`、次に `quarantine --accept-current-files` で選択するまで開きません。（例外が 1 つあります。Windows 形式の切り替えがファイルを 1 つも移動する前に失敗し、諦める際に別のプログラムの変更を見つけた場合でも、自分のジャーナルは削除します。切り替えのものは何も適用されておらず、別のプログラムの変更は残り、アプリログには "Book switch ... was retired without recording recovered" で始まる警告が出ます。）

**Windows、および名前を交換できないファイルシステム（"v3" ジャーナル）。**
これらは各ファイルを 2 回のリネームで公開します。まず旧ファイルをステージングフォルダーの `old-<i>` にリネームし、次に新ファイルを所定の場所へ移します。プレースホルダーはないため、2 回のリネームの間でクラッシュすると本のファイルが一時的に存在しなくなります。復旧は上記と同じ規則に従います。保存された旧ファイルを確認し、配置済みの新ファイルを `discard-<i>` に退避して旧ファイルを戻します。ジャーナルがすでに `committed` なら前向きに完了します。[`_recover_book_journal`；交換が使えない場合 `apply_book_state_locked` は v3 を選び、これにはすべての Windows の切り替えが含まれます。]

これらはすべて #1816 の 1 つの規則に従います。復旧は、自分たちのものと証明できなくなった名前の上にリネームすることは決してありません。どのファイルが自分たちのものか判断できないときは、ジャーナル、ステージングフォルダー、両方のファイルを保持し、推測せずに本を開くことを拒否します。

## 切り替え中の読み取り側

Linux または macOS でファイルを作成または削除している間、その名前は一時的に 64 バイトのプレースホルダーを持つことがあります。テキスト `alexandria-book-placeholder-v1 `、ランダムな id、改行です（`app/book_placeholder.py`）。これは決して実際の内容ではありません。アプリのほとんどの読み取り側は、本のロック（`ensure_book_state`）を取得してから本を読むため、保留中の切り替えを先に完了または拒否し、プレースホルダーを見ることはありません。ロックなしで動く少数の読み取り側はそれを確認します。

- **ダウンロードとエクスポート**は、プレースホルダーを配信する代わりに 409 `SWITCH_IN_PROGRESS`（「A book switch is in progress. Wait a moment and download again.」）を返します。ルート（HTTP の経路）は名前を確認し（`_require_export_download`、`app/routers/editor.py`）、レスポンスは実際に開いたファイルを確認する（`ExportFileResponse`、`app/export_download.py`）ため、その間に始まった切り替えも捕捉されます。ZIP ダウンロードはプレースホルダーファイルをスキップし、すべてがプレースホルダーなら 409 を返します（`build_zip_download`）。
- **チャンク読み取り**（`ProjectManager._read_chunks`、`app/project.py`）は「A book switch is in progress; chunks are not available yet」で拒否します。プレースホルダーを解析したり、破損としてリネームしたり、その上に再生成したりせず、名前ではなく読み取ったバイトを確認するため、途中の交換も捕捉されます。
- **スコープエクスポート**は、プレースホルダーの `state.json` を「まだインベントリがない」として扱います（`is_scope_export_historical`、`app/project_scope_exports.py`）。

## 復旧コマンド

Alexandria フォルダーのターミナルで、アプリの Python を使って実行します（Pinokio では `app/env` の環境）。

```
python app/book_state_recovery.py inspect --hash
python app/book_state_recovery.py finish
python app/book_state_recovery.py quarantine --accept-current-files
python app/book_state_recovery.py migrate-legacy --trust-journal-hashes
```

| コマンド | 内容 |
|---|---|
| `inspect` | 読み取り専用のレポート：保留中のジャーナル、各ファイルの期待状態と現在状態、作業フォルダー、受領書付きの各退避フォルダー、クラッシュの残骸（`orphaned_staging`、`journal_temporaries`）。`--hash` を付けると各ファイルをハッシュし、ジャーナルの `old` バイト、`new` バイト、`neither` のどれを持つかを報告します。タイムスタンプだけでは同じサイズの書き換えを見逃すことがあります（FAT/exFAT は 2 秒単位の時刻を保持します）。`--no-lock` はアプリがビジーな間にベストエフォートのスナップショットとして読み取ります。表示されるエントリは実行中の切り替えのステージングかもしれません。 |
| `finish` | アプリが実行するのと同じ復旧を今すぐ実行します。 |
| `quarantine --accept-current-files` | 本のファイルがジャーナルと一致しなくても、現在のまま保持します。作業フォルダーとジャーナルは退避され、何も削除されず、本は開きます。`inspect` で現在のファイルが望むものだと確認した後に使います。 |
| `migrate-legacy --trust-journal-hashes` | 旧バージョンのアプリのジャーナル（v1）用です。v1 は各ファイルのハッシュを記録しますが同一性は記録しません。このフラグを付けると、そのフェーズが記録したハッシュを持つファイルが信頼されます。すべてのファイルが一致すると、作業フォルダーと旧ジャーナルは `.book-switch-migration-<hash>-<nonce>/` に移動され、本は開きます。公開の途中で中断した保存はどちらの状態にも一致せず、一致しない各ファイルが一覧表示され、何も移動しません。 |

共通オプション：`--json` は 1 つの JSON オブジェクトを出力し、`--data-dir DIR` はデータフォルダーを指定し（既定はアプリ自身のフォルダー：`ALEXANDRIA_DATA_DIR`、なければ Alexandria フォルダー）、`--wait SECONDS` は別の本の操作が終わるまで待ちます。`--wait` を付けない場合、ビジーなアプリはハングせずにすぐ報告されます。

| 終了コード | 意味 |
|---|---|
| 0 | 完了、または保留中のものがない。 |
| 1 | システムエラー。不確定なジャーナル書き込みを含む（証拠は保持；再試行）。 |
| 2 | 使い方のエラー。確認フラグの不足など。 |
| 3 | 拒否。メッセージが理由を示し、何も移動していない。`inspect` がジャーナルを読めない場合も返る。 |
| 4 | ビジー：別の本の操作がロックを保持している。 |
| 5 | 旧版 v1 ジャーナルが保留中。`migrate-legacy` を使う。 |

## 退避フォルダー

各 `.book-switch-quarantine-*` または `.book-switch-migration-*` フォルダーには次が入ります。

- `receipt.json`：移動中は `prepared`、完了後は `completed`。ジャーナルのハッシュとフェーズ、移動理由も記録します。操作者による隔離では `forced` が true、移行では `kind: legacy-migration` と `trust: journal-digests` が追加されます。
- `journal.json`：ジャーナル自体。コピーではなく移動されるため、バイト単位で同一です。
- `workspace/`：存在した場合の作業フォルダー（移動済み）。

アプリはこれらのフォルダーを決して削除しません。証拠が不要になったら自分で削除してください。`inspect` はすべてを一覧表示します。ジャーナルがまだデータフォルダーにある間に移動が中断した場合、次の復旧（隔離）または同じコマンド（操作者による隔離、移行）がそれを完了します。ジャーナル移動後に停止した場合、次の本の操作（または `finish`）が受領書を完了しますが、`journal.json` が受領書が記録した正確なサイズとハッシュを持ち、`workspace/` が受領書の指すフォルダーであることを再確認した場合に限ります。証明できなければ受領書は `prepared` のままで、何も移動せず、`inspect` はそのフォルダーに `journal_held: true` を表示します。

## 信頼境界

受領書は署名されていません。データフォルダーに書き込める人はすでに本のファイルを変更できるため、これらのツールはそのフォルダーを信頼します。受領書の `forced` フラグは、作業フォルダーが実際に移動された後にのみ尊重されるため、手書きの受領書で通常の復旧を強制隔離に変えることはできません。
