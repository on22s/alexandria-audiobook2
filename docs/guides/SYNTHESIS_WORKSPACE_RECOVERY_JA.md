# 使い捨て合成ワークスペースの復旧

Linux 上の所有ローカル合成ウィンドウは、音声を書き込む前に作業用 WAV を登録するようになりました。対象の種類は custom、clone、design、LoRA、ensemble です。プロセスが落ちると、次にアイドル状態で起動したアプリ、または音声タスクの受け入れ時に、検証済みの使い捨てファイルを回収します。再利用可能なセグメントの復旧が無効な場合も同様です。そのため再試行は、保存済みのテイクや再利用可能なキャッシュの証拠を消さずに、放置された作業コピーを削除できます。

対象となるローカル Project の経路では、生の親 WAV にも独自の登録があり、ファイルを確保する前に作られ、エンコードと最終的な選択テイクの公開を通じて保持されます。内側のウィンドウは別のワークスペースを使い、それらのウィンドウを終えても生の親は退役しません。生の親の所有権は、任意の合成ウィンドウや再利用可能な復旧とは独立しています。両方の機能をオフにした既定のレンダリングでも、使い捨ての後片付けに必要な実行中のタスク、本、UID、入力の権限を記録します。再利用可能なキャッシュ、発話入力の取得、公開の証明に関するポリシーは変わらず、所有権だけではこれらの任意機能は有効になりません。

元の Project のチャンクエンコーダーでは、同じ親の登録が、エンコードされた中間ファイルとそのエンコーダーの一時領域も所有します。別のワークスペースを確保したり、並列親の予算を減らしたりはしません。MP3 のエンコードと WAV へのフォールバックは、既存の選択スロットへの公開で結果を `voicelines` に移すまで、そのワークスペース内にとどまります。そのため公開前の強制終了では、登録されていない `.chunk-*` や `.render-*` ファイルではなく、所有された一時領域が残ります。エンコーダーは、検査済みの no-follow ディスクリプターを通して生の親を読みます。PCM、出力、エラーの各ファイルは排他的に作成され、子は読み取りや切り詰めの前に、登録された inode の同一性を確認します。WAV へのフォールバックも、完了したファイル名が自分が書いたファイルをまだ指していることを確認します。完了した inode は、選択スロットへの公開を通じて開いたままです。どちらの rename も固定した送信元と送信先のディレクトリーを使い、選択された送信先はメタデータを変更する前にその同じ inode を指している必要があります。差し替えは証拠として保持され、有効な音声としてデコードできるというだけで成功したテイクになることはありません。子は、既存の上限付きエンコーダーメタデータファイルに、フラッシュ済みの出力バージョンを記録します。WAV へのフォールバックは、公開のロックの外で、キャンセル可能なブロック単位に、保持したディスクリプターを通してコピーしたバイトを検証します。相対 import は、子が固定した一時領域に入る前に凍結されます。起動時のカレントディレクトリーは起動前に記録されるため、後からカレントディレクトリーが変わってもそれらの import の向き先は変わりません。上書きされたチャンクの読み取り、エンコーダー、ファイル公開のヘルパーは既存のステージングの挙動を保ち、この追加のエンコード権限は渡されません。

記録されたのと同じ権限は、custom、clone、design、LoRA、ensemble の対象となるローカル Project のバッチ出力にも及びます。対象の各行には、ディスパッチの前に別々の親ワークスペースが確保され、すべてのバッチ終了処理を通じて保持されます。ネイティブのリストバッチ、長さによる並べ替え、サブバッチ、OOM 時のサイズ縮小は変わりません。内部の経路は、プロジェクトのディレクトリー、インデックス、実行中のクレームを登録されたパスに結び付けます。発話入力の取得も同じパスを使います。対応付けのない行は通常の出力パスのままです。上書きされたバッチ書き込みには、登録された出力経路は渡されません。

レジストリーはプロジェクトのデータルートにある `.synthesis-workspaces-v1/registry.json` です。不透明なワークスペース ID、ハッシュ化したクレーム／本の来歴、ディレクトリーの同一性、宣言されたウィンドウ数を記録します。ソースのテキストは含みません。後片付けは既存のカーネルのタスクリースと本のロックを使い、実行中のタスクや使用中の本があるとメンテナンスを延期します。通常のキャンセルでは同じ所有者の使い捨てワークスペースを片付け、所有者が取り消された場合は後のアイドル時の操作に残します。

別の `.synthesis-recovery-v1` キャッシュは、再利用可能な検証済みセグメントを保存します。そのキャッシュを消しても、ほかのファイルの削除が許可されるわけではありません。完了した親の公開と保存済みテイクの関連付けは、既存の所有権チェックを保ちます。ワークスペースの後片付けに失敗してもログに記録されるだけで、公開済みの親が失敗したレンダリングになることはありません。

ウィンドウが 0 個の行は、親だけのワークスペースを宣言します。通常のウィンドウの行は、2 個から 1,024 個のウィンドウを宣言します。ウィンドウが 0 個の行を拒否する古いアプリケーションのバージョンは、レジストリーを片付けずに保持します。自動メンテナンスを再開するには、親の行を理解するバージョンを使ってください。

エンコードが有効な新しい親の行には、明示的な `encoding: true` の印があり、書き込みが動く前に両方のディレクトリーの同一性と一緒にコミットされます。既存の非公開の `join` ディレクトリーがエンコーダーの一時ディレクトリーです。古い 5 フィールドの行は、元の厳格な join ファイルの規則を保ちます。エンコードの印を認識しない古いクライアントは、レジストリーを保持し、新しい登録済みの確保を拒否します。ダウングレードの前にアイドル時のメンテナンスを終えるには、エンコードを理解するバージョンを使ってください。保存済みのテイクと再利用可能な復旧の証拠は、これらの使い捨ての行とは別です。

退役は、登録時に記録した正規の本のルートとディレクトリーの同一性を使います。本のルートのシンボリックリンクを付け替えても、後片付けを別の本へ誘導することはできません。ルートが置き換わったり所有者が取り消されたりした場合、受け入れ済みのアイドル時の復旧のために元の課金対象の登録を保持します。後片付けは移動したディレクトリーを探したり、権限を失った後に強制的に削除したりしません。

## 上限と保持される証拠

- 登録できるワークスペースは最大 256 個で、各ワークスペースのウィンドウは最大 1,024 個です。これは使い捨てストレージの受け入れ上限であり、要求した並列ワーカーの設定は変わりません。上限に達すると、作業用音声をこれ以上確保する前に、対象のレンダリングを拒否します。
- 親と内側のウィンドウの登録は、この 256 ワークスペースの予算を共有します。対象のウィンドウを使う Project のレンダリングが動作中なら、2 つのスロットを占めることがあります。容量の拒否が、登録されていない親ファイルへフォールバックすることはありません。
- 対象のバッチ行はそれぞれ 1 つの親スロットを占め、分割された親をレンダリングしている間は内側のウィンドウのスロットも占めます。現在のバッチ試行のすべての親スロットは、プロバイダーの処理より前に受け入れられる必要があります。OOM の再試行は新しいスコープと登録を使い、以前の試行のパスは再利用しません。
- 使い捨てなのは、登録されたウィンドウのファイル、非公開の組み立て済みの親、固定の join 一時領域、および宣言された WAV 設計の公開ステージングファイルだけです。未知のファイル、シンボリックリンク、ハードリンク、変わったディレクトリーの同一性、不正または欠落したレジストリーの権限は保持されます。
- エンコードの印がある親の行は、固定のエンコード済み、PCM、エンコーダーエラーのファイル名も宣言します。固定された非公開の join ディレクトリーは、最大 16 個の通常の、単一リンクの、現在のユーザーの一時ファイル（合計最大 8 GiB）をエンコーダーに委ねます。入れ子のディレクトリー、別名、過剰な一時領域、安全でない項目があると、登録全体が保持されます。宣言されたすべての子は最初の削除の前に確認され、印は過去のファイルを引き継ぎません。
- ディレクトリーの作成とその同一性のコミットの間でクラッシュすると、空の曖昧なディレクトリーと予約済みのスロットが残ることがあります。同一性をコミットする前に、どのプロバイダーも音声を書くことはできません。このスロットは明示的な検査のために予約されたままになり、後片付けは名前から権限を推測しません。
- 既存の未登録の `.synthesis-render-*` と `.synthesis-join-*` ディレクトリーは手を付けません。手動で削除する前に、アプリを停止した状態で既知のパスを検査してください。共通のファイル名の接頭辞だけを根拠に、保存済みのテイクや復旧の成果物を削除しないでください。
- 自動の回収は現在、Linux 上の既知の未変更のローカル種類（custom、clone、design、LoRA、ensemble）を対象にしています。Windows/macOS、上書きされたプロバイダー、リースなしで直接呼び出す Python は、通常の一時ファイルの挙動のままです。まだハードクラッシュからの回収について主張できる認定はありません。
- Ensemble の登録は、たとえ上書きされた種類がその ensemble に含まれていなくても、通常の custom、clone、design、LoRA のメンバーの書き込みが未変更であることを保守的に要求します。そうでなければ通常の一時パスを保持します。対象の ensemble は 1,024 ウィンドウの上限を超えられず、登録されていないフォールバックで上限付きストレージを回避するのではなく、拒否します。
- Ensemble のメンバーの一時領域と Project の design プレビューは、登録されたウィンドウのワークスペースを使います。Designer タブの `designed_voices/previews` 以下にあるプレビューは、別のステージング経路のままで、このレジストリーの対象ではありません。
- 対象のローカル種類のパスの外にあるバッチ行、リースなしの直接呼び出し、`voicelines` の従来のステージング、チャンクエンコーダーの外にある章の書き出し／PCM の書き出し／結合は、この登録の対象外です。既存の未登録の親ファイルは保持され、この変更が履歴ファイルのファイル名に基づく後片付けを許可することはありません。

警告は、保持された登録や利用できないレジストリーの権限を示します。診断のために、それらのパスとメタデータを保管してください。アプリケーションは、壊れたレジストリーをリセットしたり、プロジェクトを再帰的に掃除したり、対象のレジストリーが満杯のときに追跡されないあふれにフォールバックしたりしません。
