# LoRA evaluation serving identity

Evaluation synthesis settings such as device: auto are not proof of how an adapter was served. New v4 evaluations record the device selected by the loader, its dispatched dtype, merged versus unmerged LoRA mode, and a serving-policy version. These fields are included in the evaluation specification hash.

The observation comes only from a successfully loaded LoRA model. Reading an adapter list or comparison never constructs a model, imports Torch, resolves devices, or probes a GPU. Unloading the model clears the observation. The scorer's --device option chooses the ECAPA scoring device, not the TTS serving mode.

- A cold engine, missing observation, changed synthesis settings, or different serving mode cannot reuse a cached evaluation as current. A cold CLI invocation therefore regenerates probes instead of guessing the mode from configuration.
- Evaluation refuses a change between probes, final scoring and publication. Backends without an observation (including the experimental MLX worker) can still produce integrity-bound historical reports and probe audio. They cannot reuse a current cache, rank candidates, promote, or remove candidates. Candidate ranking and cleanup require one common observed mode across all evaluated checkpoints.
- Older integrity-valid v4 evidence without a serving identity remains historical and auditionable. Matched historical comparison, blind listening and review history remain available; tampered evidence is still refused.
- The model list shows stored results neutrally as historical, even when the mode matches. It does not hash every adapter's weights just to paint the list. A mode match enables a promotion attempt, but comparison and promotion independently validate full evidence. Unknown or mismatched modes disable promotion; the server also refuses before checkpoint mutation.
- Current on a comparison means both full records match the observed mode and configured synthesis settings at validation time. It is not listening acceptance, hardware qualification, or a voice-quality guarantee. A later unload or switch requires revalidation.

Promotion captures the server engine, configured settings and observed mode for that request before the owned GPU claim releases idle models. The locked publication validates the same engine and settings and fully checks both evidence records against that admission observation. It does not retain a global observation after unload or accept a client-supplied serving identity.

Probe attempts use unique filenames. Failed evaluation or publication removes only unreferenced files from that attempt, leaving existing reports and referenced audio intact. When the first generated probe still has no serving observation, an integrity-valid existing report is retained as historical without scoring another evaluation, ranking, cleanup or a pipeline error. That first probe is necessary because a cold engine is not proof of an unobserved backend; it is removed afterward. `--overwrite` explicitly permits replacement instead. An invalid existing report requires explicit overwrite and is never accepted as historical evidence. Failed replacement before publication preserves the manifest evaluation/recommendation and bytes, reporting the attempt failure through stdout and the exit status; the UI continues to display the preserved old report. A failure after publication begins records a failed manifest summary without a stale recommendation. Successful replacements retain earlier probe files rather than deleting potentially auditioned historical audio, so repeated successful evaluations can increase disk usage. Newly unranked historical reports preserve audio on disk but do not create a ranked comparison or a promotion recommendation; existing matched historical comparisons remain available. Stored failed evaluation summaries show their failure badge and warnings. Generate a LoRA test line inside the app and press Refresh to observe its current mode; CLI evaluation cannot create an observation in the server process. Re-evaluation is needed only when the report does not match that observed mode/settings.

An interrupted unobserved evaluation may leave only candidate reports. A rerun preserves each valid historical candidate report and publishes the missing historical production report without ranking or cleanup. A corrupt report does not retain new, uniquely named audio from an aborted attempt; older audio is untouched. If a report is unreadable or an attempt file is locked, cleanup reports the filesystem error, returns a failing batch status and continues with the remaining adapters rather than hiding the original evaluation failure.

The in-app evaluate stage deliberately has no overwrite toggle. Invalid existing evidence on an unobserved backend therefore stops that stage; it is not a successful historical no-op. Preserve any report/audio you need, then explicitly rerun the CLI evaluator with its manifest, models directory and configuration arguments plus `--overwrite` before retrying the pipeline. Repeated in-app retries alone do not repair corrupt evidence.

This repairs evidence identity only. It does not qualify CUDA, change LoRA audio generation, add recovery certificates for unmerged serving, or close the wider #1710 investigation.
